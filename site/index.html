Why it’s different

Most vaults protect your secrets with a promise. Remotino protects them with math.

The usual model is a trusted server that can decrypt everything — one break and every credential is readable. Remotino inverts that: the store is untrusted, and permission is a property of the keys, not a setting.

Zero-trust storage

The database only ever sees ciphertext.

Every folder and credential is sealed on your machine before it leaves. Sharing means wrapping a content key to a teammate’s public key — so “who can read this” isn’t an access-control list the server enforces, it’s who mathematically holds the key. Compromise the database and you get encrypted blobs, not passwords.

Embedded, not a launcher

Your password never leaves the process you trust.

RDP and SSH render inside the app. The credential is unsealed in memory and used to authenticate — it’s never handed to an external client you don’t control.

Tamper-evident

An audit log that can’t be quietly rewritten.

Every change is a signed link in an append-only hash chain, and the database itself denies UPDATE and DELETE. Rewriting history isn’t against the rules — it’s cryptographically detectable.

Everything in one place

A daily driver first, a security tool underneath.

Built to replace a connection manager that crawls at a hundred entries — fast tree, instant filter, command palette — without asking you to think about the crypto holding it together.

RDP + SSH, unified

Embedded remote desktops and live terminals in one tabbed window. Dynamic resize, remote cursor, Ctrl+Alt+Del, clipboard.

Credential vault

Passwords and SSH keys, each sealed under its own key. Auto-fills on connect — the secret never touches the UI.

Share by public key

Grant a folder or a single credential to a teammate. Revoke it again. Access follows the keys, not a toggle.

Flexible backends

Solo on a local encrypted store, or a shared append-only repository on MSSQL Server or PostgreSQL. Each user gets a least-privilege login — SELECT/INSERT only — so the log stays server-enforced.

Set up in the app

Initialize the database and provision users from the GUI — no SSMS or psql. Each user’s password is a “setup code” safe to send over chat, and the server’s TLS certificate is pinned on first use.

Command palette

⌘K to jump to any host. A tree that filters instantly and drag-drops to reorganize, even at thousands of entries.

Windows & macOS

Native on both, one small binary each, the same embedded RDP engine. Plus an SSH-only terminal client.

Modern crypto only

Ed25519, X25519, XChaCha20-Poly1305, Argon2id. No RSA, no shared application login, nothing to extract from a config file.

Under the hood

The security is the architecture, not a feature bolted on.

Nothing here trusts the storage layer. The primitives are boring, modern, and named on purpose.

Identity
An Ed25519 signing key + X25519 wrapping key, sealed at rest with Argon2id. Unlocked by your passphrase — never stored, never sent.
Content
Folder names and connections sealed with XChaCha20-Poly1305 under per-folder and per-credential keys.
Sharing
Content keys wrapped to a recipient’s public key (ECIES). Only the holder of the private half can unwrap — and it never leaves their machine.
Audit
A signed hash chain. Append-only is server-enforced — the database denies UPDATE and DELETE on the log.
Backend
MSSQL Server or PostgreSQL holds opaque bytes and per-user least-privilege logins, over pinned TLS. It is treated as untrusted storage, not a trusted authority.

Why append-only matters

Each entry signs the hash of the one before it. Change any past record and every later link stops verifying — and because the database itself refuses to rewrite rows, tampering isn’t just detectable, it’s blocked at the source.
