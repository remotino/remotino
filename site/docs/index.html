Remotino — User Guide

An encrypted RDP & SSH connection manager. Your connections and secrets are sealed on your machine before they ever reach a server — access is enforced by keys, not by rules a database could be tricked into ignoring.

1 · First run

Install

Remotino is portable. Unzip the build and keep the two files together: remotino-app.exe (the app) and rdp-host.exe (the RDP engine, which the app launches — it must sit next to the app). Double-click remotino-app.exe. On Windows 11 nothing else is needed; on Windows 10, if the window is blank, install Microsoft's Evergreen WebView2 Runtime.

Create your identity

On first launch you'll create a new identity with a passphrase. That passphrase unlocks a key pair that seals everything you store — it is never saved and never sent. If you forget it there is no reset, so keep it somewhere safe. By default everything is stored on this machine in a local encrypted store; no server is required to start.

Add connections

  • Create folders and connections from the tree or toolbar. Folders nest; drag to reorganise.
  • A connection has a kind (RDP or SSH), a name, a host, and a port.
  • Press Ctrl+K (⌘K on macOS) for the command palette, and use the filter box to narrow the tree instantly.

Open a connection for an embedded session in a tab — an RDP desktop (dynamic resize, remote cursor, a Ctrl+Alt+Del button) or an SSH terminal.

The credential vault

Store a password or SSH key once and link it to connections; Remotino fills it in on connect. Each credential is sealed under its own key and decrypted only inside the app's backend at connect time — the secret never reaches the on-screen UI, and never sits inside a connection definition (only a reference does).

2 · Setting up a shared backend

A shared backend lets a team work from one repository and share folders and credentials. Remotino supports MSSQL Server and PostgreSQL. The database only ever holds encrypted blobs and a per-user, least-privilege login — untrusted storage, not a trusted authority. Do this once, as the admin.

1 · Point Remotino at the database

Open Connection settings and pick SQL Server or Postgres. Enter the host, port, and database (for SQL Server, an optional instance). The default port fills in (1433 / 5432).

TLS (Postgres)

Tick Require TLS, then Verify certificate. Remotino shows the certificate's SHA-256 fingerprint, subject, issuer and validity. Compare the fingerprint out of band, then Trust this certificate. This is trust-on-first-use pinning (the SSH known-hosts model): you approve the exact certificate once, and any later change is refused. The pin travels inside setup codes, so provisioned users trust the same certificate.

2 · Initialize the database

Click Set up / add users… and sign in with admin rights once (nothing is stored): Windows/sa for SQL Server, or a superuser like postgres for Postgres. Click Initialize database — Remotino creates the database if missing, the tables, a least-privilege remotino_user role, and its SELECT/INSERT grants. Append-only is enforced by the database itself: UPDATE, DELETE and TRUNCATE on the log are rejected.

3 · Provision your own login

Under Provision a login, leave the target as Yourself and click Create login. Remotino creates a least-privilege login with a strong random password sealed to your identity — nothing shown or typed — and switches you to it. Click Save; the app locks and reopens on the shared backend.

TipIf you had local connections, Remotino now asks whether to bring them along — see Migrating bookmarks.

3 · Bringing your local bookmarks along

If you've used Remotino on This machine and then switch to a shared backend, your folders, connections and vault are in the local store — the shared database starts empty. So when you save a local→shared switch with local entries, Remotino asks:

Bring your bookmarks along?
Your local store has N connections, M credentials and K folders. Copy them into the shared database so it isn't empty?
Start freshBring them along

What actually happens

The local store and the shared database are two separate signed hash chains, so raw entries can't be transplanted. Instead Remotino replays them: it decrypts your local tree and vault with your unlocked identity and re-creates each folder, connection and credential as new events on the shared chain (fresh ids, re-sealed content), preserving hierarchy and credential links. Your local store is left untouched.

One-way, into an empty repositoryMigration refuses if the shared database already has entries, so it can never duplicate a tree. If a colleague already populated the shared repository, choose Start fresh and you'll get access to shared folders as they're granted to you.

4 · Adding users

The admin gives each teammate two things: an enrolment (so they can be granted access cryptographically) and a login to the database.

  1. The teammate sends their identity. They open the Users panel (the people icon), and under Your identity click Copy and send you the string. It's a public key — safe over any channel. They should also set a display name so you can share things back to them.
  2. You enrol them. In your Users panel, under Enrol a user, type their name, paste their identity string, and click Enrol.
  3. You give them a login. Next to the enrolled user, click Setup code. Remotino provisions a least-privilege login with a random password sealed to their identity, and packages the host, database, sealed password and (for Postgres) the TLS pin into one setup code. Send it — it's safe over chat.
  4. They apply the code. In Connection settings they pick the same backend, click I have a setup code instead, paste, Apply code → Save.
Why two stepsEnrolment is cryptographic access — it lets you wrap folder and credential keys to that person. The database login is about reaching the store at all, with least privilege (SELECT/INSERT). Even with a login, a user reads only the ciphertext of folders they hold a key for.

5 · Sharing folders & credentials

Granting a folder or credential wraps its content key to the recipient's public key, so "who can read this" is who mathematically holds the key — not a flag the server enforces. You can share with anyone you've enrolled.

Share a folder or credential

Right-click a folder or credential in the tree and choose Share…. Toggle a user on to grant, off to revoke. Granting a credential lets a teammate use it to connect without ever seeing the secret — it's decrypted only inside their app at connect time. Shared items show a small shared tag.

Revoking

Revocation is forward-only. It stops the user from reading future changes, but treat anything they already had as known to them. For a credential that must be truly retired, rotate the secret on the host after revoking.

What a compromised server sees

Nothing useful: encrypted names and connection details, content keys wrapped to public keys (unusable without the private half, which never leaves a user's machine), and a signed append-only chain. Compromise the database and you get ciphertext and the shape of activity — never a password.

Auditing

The toolbar's audit log shows every change — when, who, and a plain-English action, newest first. It re-walks the signed hash chain and shows a Chain intact badge, flipping to Tampering detected if any row was deleted, reordered or edited.
